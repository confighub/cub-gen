# v0.4 Working Roadmap: Component -> Deployable Variant -> Proof

Status: connected roadmap draft; OpenChoreo and app-of-apps vertical slices implemented on this branch
Date: 2026-04-30
GitHub milestone: [v0.4: Component -> Deployable Variant -> Proof](https://github.com/confighub/cub-gen/milestone/4)
GitHub parent issue: [#287](https://github.com/confighub/cub-gen/issues/287)

This is a working title, not golden ConfigHub product language. The goal is
simpler than the title: make `cub-gen`'s role and value obvious.

Hard quality gate added from an OpenChoreo-team review: do not claim
OpenChoreo credibility until the README is honest about support status, the
adoption path starts read-only, an OpenChoreo-shaped fixture proves the hard
case, and generated-resource ownership/edit routing is modeled.

Current implementation note: this branch adds a fixture-backed OpenChoreo
adapter, `gitops discover --adoption-report`, OpenChoreo field-route proof, a
fixture-backed app-of-apps adapter, a read-only multi-repo platform-estate
import graph, manifest-driven variant fanout for Helm/Score/Spring, enrichment
sidecars, and golden parity coverage. It is not yet full upstream OpenChoreo
conformance or implicit/glob-based variant discovery.

## Product Promise

`cub-gen` starts from the repo or platform inputs a team already has and shows:

```text
Component
  -> Deployable Variant
      -> Target
      -> Connections
      -> Change
      -> Proof
```

In plain English:

1. what reusable thing exists,
2. what concrete deployable copies or contexts it has,
3. where each copy runs or reconciles,
4. what each copy is wired to,
5. what change is being proposed,
6. what proof explains origin, ownership, impact, and decision.

The generator model remains the implementation explanation underneath this user
model. Users should not need to understand DRY/WET/generator contracts before
they understand why `cub-gen` is useful.

shipped, planned, or only documented as a worked example.

This is the core model work. It should precede OpenChoreo/app-of-apps adapter

objects, not only as generator internals, and can start with a read-only report
for an existing platform before proposing annotations or rewrites. The branch
now emits one standard change bundle per declared variant and lets
`change explain` scope a fanout file with `--variant`.

## Parallel Work

These can run at the same time:

1. Phase 0 docs/teaching and Phase 1 connected trust.
2. OpenChoreo docs honesty work and the read-only adoption-report design.
3. OpenChoreo and app-of-apps adapter exploration after the platform graph shape
   is agreed, as long as OpenChoreo fixture and ownership-route proof are not
   skipped.
4. GUI provenance trace, route badges, and mutation history once enrichment
   output has a stable shape.

These should be sequential:

1. Platform import graph before broad variant fanout.
2. Connected trust before PR/MR linkage is presented as the main demo path.
3. Honest OpenChoreo docs before README claims OpenChoreo support.
4. OpenChoreo hard fixture before the OpenChoreo adapter is called credible.
5. Route metadata before server-side route enforcement.
6. Server-side enforcement before GUI refresh preview claims trust.

## Exit Criteria

The roadmap is ready when:

1. the README, docs index, examples index, and GitHub issue queue all tell the
   same story,
2. a user can start with a repo and discover Components, Deployable Variants,
   Targets, Connections, Changes, and Proof,
3. at least one connected path proves the PR/MR and decision story without
   special backend surprises,
4. implemented examples distinguish product proof from worked-example teaching,
5. OpenChoreo support claims are either removed or backed by runnable fixture
   proof, generated-resource ownership, and explicit edit routing,
6. the command surface no longer makes `cub-gen` feel like a separate idea from
   ConfigHub.
