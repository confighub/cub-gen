# cub-gen v0.2-preview.2 Release Plan

Status date: 2026-04-11
Latest release: `v0.2-preview.1` (2026-03-06)
Next target: `v0.2-preview.2`

This plan supersedes `docs/roadmap-v0.2-preview.md` for active release planning.
For day-to-day release closure, use
[`docs/releases/v0.2-preview.2-ship-checklist.md`](v0.2-preview.2-ship-checklist.md).

## Release goal

Ship a preview that feels trustworthy as a product surface, not only as a
parity-locked slice.

For `v0.2-preview.2`, that means:

1. every featured example works well enough to recommend with confidence,
2. the CLI and docs are intuitive in a clean checkout,
3. release/readiness claims are backed by real checks instead of stale issue
   lists or routinely skipped CI lanes.

## Must-ship workstreams

### 1. CLI and docs trust

Goal: the first commands a user sees should work exactly as documented.

Landed on `main`:

- [#232](https://github.com/confighub/cub-gen/issues/232) README structure
- [#233](https://github.com/confighub/cub-gen/issues/233) help-text duplication
- [#234](https://github.com/confighub/cub-gen/issues/234) remove stale prototype framing
- [#237](https://github.com/confighub/cub-gen/issues/237) answer current variants/overlays behavior clearly

Required outcome:

- broken example strings such as `local-renderer` / `render-target` are removed
  or made real,
- root help and subcommand help are short, consistent, and accurate,
- README and getting-started docs lead with value and working commands,
- the repo no longer describes `cub-gen` as a whole as a prototype/proposal.

### 2. Full example-catalog quality bar

Goal: "all examples working well" means the whole catalog is trustworthy, not
only the flagship path.

Current open issues:

- [#177](https://github.com/confighub/cub-gen/issues/177) Helm flagship
- [#180](https://github.com/confighub/cub-gen/issues/180) workflow examples
- [#187](https://github.com/confighub/cub-gen/issues/187) Kubara-like layered provenance

Landed on `main`:

- [#182](https://github.com/confighub/cub-gen/issues/182) entrypoint redesign
- [#185](https://github.com/confighub/cub-gen/issues/185) custom-generator onboarding
- [#200](https://github.com/confighub/cub-gen/issues/200) AI best-practice alignment
- [#202](https://github.com/confighub/cub-gen/issues/202) AI-first flagship surfaces
- [#178](https://github.com/confighub/cub-gen/issues/178) Score standalone runtime proof
- [#207](https://github.com/confighub/cub-gen/issues/207) Spring block/escalate proof
- [#208](https://github.com/confighub/cub-gen/issues/208) Spring embedded-config mutation support

Required outcome:

- all featured examples have a clear local path and connected path,
- every example ends in something a user can inspect live or an explicitly
  documented lower proof tier,
- every example shows at least one governed outcome,
- docs and entrypoints explain who the example is for and why the example
  matters,
- unresolved product gaps are called out honestly instead of hidden behind
  generic connected-proof language.

### 3. Credible connected release signal

Goal: decide what the connected release gate really proves, then make it
credible.

Current open issues:

- [#218](https://github.com/confighub/cub-gen/issues/218) provision secrets and get a green connected run

Landed on `main`:

- [#226](https://github.com/confighub/cub-gen/issues/226) standard ConfigHub API/CLI over custom bridge endpoints
- [#227](https://github.com/confighub/cub-gen/issues/227) rethink the size and purpose of `ci-connected`

Required outcome:

- the project deliberately replaces the old `ci-connected` release claim with a
  smaller connected smoke lane and updates docs/status claims to match,
- the smaller smoke lane is something the team can actually run in the intended
  release environment,
- deeper connected stories, flow proofs, and live reconcile checks remain
  available as an explicit non-release lane,
- release notes and README wording stop implying that a skipped lane is an
  active release proof.

## Exit criteria

`v0.2-preview.2` is ready to cut only when all of the following are true:

1. `make ci-local` is green on `main`.
2. `mkdocs build --strict` is green in the release environment.
3. Top-level help and subcommand help examples have been exercised from a clean
   checkout.
4. README, docs index, release plan, and release notes agree on what is open,
   what is shipped, and what is still partial.
5. The example catalog has no silent second-class entries: each featured example
   has a start path, an inspection target or honest proof-tier note, and a
   governed-change story.
6. Connected release status is backed by a lane the team actually runs and can
   explain.

## Planned release sequence

1. Finalize the remaining flagship example gaps and issue narrowing.
2. Confirm the release-environment connected smoke lane.
3. Run strict docs/help checks from the release environment.
4. Cut `v0.2-preview.2` release notes from a green `main`.
